To ensure platform stability and fair usage for all customers, the Trayce API enforces rate limits on a **per API key** basis using a sliding window algorithm. When a limit is exceeded, the API returns a `429 Too Many Requests` response with headers that tell you exactly when you can resume. Building retry logic around these headers keeps your integration resilient without impacting other customers.

---

## Rate Limit Tiers

Global request limits vary by plan. All limits apply **per API key** per 60-second window unless otherwise noted.

| Plan | Request Limit | Window |
|------|--------------|--------|
| **Starter** | 100 requests / min | 60 seconds |
| **Business** | 1,000 requests / min | 60 seconds |
| **Enterprise** | Custom | Negotiated |

Upgrading your plan increases the limit for all API keys associated with your account. If you need higher limits before upgrading — or you are on the Enterprise plan — contact [support@trayce.io](mailto:support@trayce.io).

## Rate Limit Headers

Every API response includes headers that let you monitor your current usage in real time. Inspect these headers proactively to throttle your own request rate before hitting a `429`.

| Header | Type | Description |
|--------|------|-------------|
| `X-RateLimit-Limit` | `integer` | The total number of requests your API key is allowed to make in the current window. |
| `X-RateLimit-Remaining` | `integer` | The number of requests remaining in the current window. When this reaches `0`, the next request will return `429`. |
| `X-RateLimit-Reset` | `integer` | A Unix timestamp (UTC) indicating when the current rate limit window resets and `X-RateLimit-Remaining` is restored. |
| `Retry-After` | `integer` | **Only present on `429` responses.** The number of seconds to wait before making another request. Always honour this value before retrying. |

Example response headers from a Business-tier key with 950 requests already consumed:

```http
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 50
X-RateLimit-Reset: 1715356800
```

Example headers on a `429` response:

```http
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1715356800
Retry-After: 14
```

## Handling 429 Errors

The recommended strategy for `429` errors is **exponential backoff with jitter** — wait for at least the `Retry-After` duration, then progressively increase the delay on repeated failures to avoid thundering-herd problems.

```javascript
async function fetchWithRetry(url, options, maxRetries = 5) {
  let attempt = 0;

  while (attempt < maxRetries) {
    const response = await fetch(url, options);

    if (response.status !== 429) {
      // Request succeeded (or failed for a non-rate-limit reason) — return as-is.
      return response;
    }

    // Respect the server-specified wait time first.
    const retryAfter = parseInt(response.headers.get("Retry-After") ?? "1", 10);

    // Add exponential back-off on top of Retry-After, plus random jitter to
    // avoid multiple clients retrying in lockstep.
    const backoff = retryAfter * 1000 + Math.pow(2, attempt) * 100;
    const jitter = Math.random() * 200;
    const delay = backoff + jitter;

    console.warn(
      `Rate limited (attempt ${attempt + 1}/${maxRetries}). ` +
      `Retrying in ${Math.round(delay)}ms…`
    );

    await new Promise((resolve) => setTimeout(resolve, delay));
    attempt++;
  }

  throw new Error(`Request failed after ${maxRetries} retries due to rate limiting.`);
}

// Usage
const response = await fetchWithRetry(
  "https://api.trayce.io/v1/verifications",
  {
    method: "POST",
    headers: {
      "Authorization": `Bearer ${process.env.TRAYCE_API_KEY}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ recipient_email: "jane.doe@example.com" }),
  }
);
```

## Endpoint-Specific Limits

In addition to the global per-key limits above, certain high-cost endpoints have their own supplementary quotas:

| Endpoint | Additional Limit | Applies To |
|----------|-----------------|------------|
| `POST /verifications` | 50 requests / min | Starter plan only |
| `POST /documents/request` | Daily cap per unique recipient email | All plans |

These limits are enforced independently from the global window. For example, a Starter-plan key that has consumed all 50 `POST /verifications` requests in a given minute will receive a `429` on the next verification creation attempt even if the global 100 req/min window still has headroom.

For `POST /documents/request`, sending multiple document requests to the same recipient email within a 24-hour period will return a `429` once the daily per-recipient cap is reached, regardless of plan tier. This cap exists to protect recipients from unsolicited requests.

<Note>
  **Enterprise plans** have fully customisable rate limits and per-endpoint quotas. Contact [support@trayce.io](mailto:support@trayce.io) to discuss your expected traffic profile and receive limits tailored to your integration's needs.
</Note>

When something goes wrong, the Trayce API returns a clear, structured error response alongside an appropriate HTTP status code. Every error includes a machine-readable `error.code` string and a human-readable `error.message` so your integration can handle failures gracefully — whether that means retrying a request, surfacing a message to the end user, or alerting your engineering team.

---

## Error Response Format

All error responses share the same JSON envelope:

```json
{
  "error": {
    "code": "string",
    "message": "string",
    "details": {}
  }
}
```

| Field | Type | Description |
|-------|------|-------------|
| `error.code` | `string` | A stable, machine-readable identifier for the error type. Use this field for programmatic handling. |
| `error.message` | `string` | A human-readable explanation of what went wrong. Suitable for logging; not guaranteed to be stable across releases. |
| `error.details` | `object` | Optional. Additional context about the error, such as which request field failed validation. |

## HTTP Status Codes

Trayce uses standard HTTP status codes to indicate the outcome of every API request.

| Status | Meaning | When it occurs |
|--------|---------|----------------|
| `200 OK` | Success | The request was fulfilled and the response body contains the requested resource or result. |
| `201 Created` | Resource created | A new resource (e.g. a verification or document request) was successfully created. |
| `400 Bad Request` | Invalid parameters | The request was malformed or contained invalid parameter values. Check the `error.details` field for specifics. |
| `401 Unauthorized` | Authentication failed | The `Authorization` header was missing, malformed, or contained an invalid API key. |
| `403 Forbidden` | Insufficient permissions | The API key is valid but does not have permission to perform the requested action. |
| `404 Not Found` | Resource not found | The requested resource ID does not exist or is not accessible with the provided credentials. |
| `409 Conflict` | Duplicate resource | A resource with conflicting unique attributes already exists (e.g. duplicate verification for a recipient). |
| `422 Unprocessable Entity` | Validation error | The request was well-formed but failed business-logic validation. Review the `error.code` and `error.details` fields. |
| `429 Too Many Requests` | Rate limit exceeded | Your API key has exceeded its request quota for the current time window. See [Rate Limits](/api-reference/rate-limits) for details. |
| `500 Internal Server Error` | Server error | An unexpected error occurred on Trayce's servers. If this persists, contact [support@trayce.io](mailto:support@trayce.io). |

## Error Codes

The following `error.code` values may appear in API responses. These strings are stable and safe to match against in your application code.

| `error.code` | HTTP Status | Description |
|--------------|-------------|-------------|
| `invalid_api_key` | `401` | The provided API key does not match any active key in the system. |
| `expired_token` | `401` | The token used for authentication has expired. Generate a new API key and retry. |
| `missing_required_field` | `400` | A required request field was omitted. The `error.details` object will identify the missing field name. |
| `invalid_document_type` | `422` | One or more values in the `document_types` array are not supported. |
| `verification_not_found` | `404` | No verification with the given ID exists, or it is not accessible with the current credentials. |
| `document_request_expired` | `422` | The document request link has passed its expiry time and can no longer be used to submit documents. |
| `rate_limit_exceeded` | `429` | The API key has exceeded its allowed request rate. Respect the `Retry-After` response header before retrying. |
| `verification_already_completed` | `409` | An action was attempted on a verification that has already reached a terminal state (e.g. `approved` or `declined`). |

## Handling Errors

Match against the stable `error.code` string — not the `error.message` or HTTP status alone — for the most reliable programmatic error handling.

```javascript
async function createVerification(payload) {
  try {
    const response = await fetch("https://api.trayce.io/v1/verifications", {
      method: "POST",
      headers: {
        "Authorization": `Bearer ${process.env.TRAYCE_API_KEY}`,
        "Content-Type": "application/json",
      },
      body: JSON.stringify(payload),
    });

    const body = await response.json();

    if (!response.ok) {
      const { code, message } = body.error;

      switch (code) {
        case "invalid_api_key":
        case "expired_token":
          throw new Error(`Authentication failed: ${message}. Check your API key.`);

        case "missing_required_field":
          throw new Error(`Bad request: ${message}. See error.details for the offending field.`);

        case "invalid_document_type":
          throw new Error(`Unsupported document type: ${message}`);

        case "verification_already_completed":
          console.warn("Verification already completed — no action needed.");
          return null;

        case "rate_limit_exceeded":
          // Caller should implement retry with back-off; see Rate Limits guide.
          throw new Error(`Rate limit hit. Retry after the Retry-After header value.`);

        default:
          throw new Error(`Unexpected API error [${code}]: ${message}`);
      }
    }

    return body.data;
  } catch (err) {
    // Re-throw for the calling layer to handle (logging, alerting, etc.)
    throw err;
  }
}
```

<Tip>
  Use the **sandbox environment** (`https://sandbox.api.trayce.io/v1` with `sk_test_` keys) to deliberately trigger and test error scenarios — including expired tokens, invalid document types, and rate limit responses — before your integration goes live. No real data or production state is ever affected.
</Tip>

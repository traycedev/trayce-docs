Trayce supports the **OAuth 2.0 client credentials flow** as an alternative to static API keys. Instead of embedding a long-lived key in your application, you exchange a `client_id` and `client_secret` for a short-lived access token. This makes credential rotation simpler and limits the window of exposure if a token is ever intercepted.

**Use OAuth when:**
- You need automatic token expiry and refresh as a security control.
- Your organization's security policy prohibits long-lived credentials.
- You are building a multi-tenant platform and need per-tenant token issuance.

**Use API keys when:** you want the simplest possible setup for internal tooling, scripts, or single-environment integrations. See [API Key Authentication](/api-reference/auth/api-keys) for details.

## Client Credentials Flow

### Step 1 — Obtain your client credentials

Navigate to the **Business Portal** → **Settings** → **OAuth Clients** and click **Create OAuth Client**. Give the client a descriptive name, then copy the generated `client_id` and `client_secret`. You will not be able to view the secret again after closing the dialog.

### Step 2 — Request an access token

Exchange your credentials for a Bearer token by calling the token endpoint.

**Endpoint**

```
POST https://api.trayce.io/v1/auth/token
```

**Request body** (`application/x-www-form-urlencoded`)

| Field | Type | Required | Description |
|---|---|---|---|
| `grant_type` | string | ✓ | Must be `client_credentials` |
| `client_id` | string | ✓ | Your OAuth client ID |
| `client_secret` | string | ✓ | Your OAuth client secret |
| `scope` | string | — | Space-separated list of requested scopes |

<CodeGroup>

```bash cURL
curl --request POST \
  --url https://api.trayce.io/v1/auth/token \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --data grant_type=client_credentials \
  --data client_id=your_client_id \
  --data client_secret=your_client_secret \
  --data 'scope=verifications:read verifications:write'
```

</CodeGroup>

**Response**

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "verifications:read verifications:write"
}
```

| Field | Type | Description |
|---|---|---|
| `access_token` | string | The token to use in subsequent API requests |
| `token_type` | string | Always `"Bearer"` |
| `expires_in` | integer | Seconds until the token expires (see [Token Expiry](#token-expiry)) |
| `scope` | string | The scopes granted to this token |

### Step 3 — Use the access token

Pass the `access_token` in the `Authorization` header exactly as you would an API key. The Trayce API treats both identically after authentication.

```bash
curl --request GET \
  --url https://api.trayce.io/v1/verifications \
  --header 'Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...'
```

## Token Expiry

Access tokens are valid for **3600 seconds (1 hour)** from the time of issuance. Once a token expires, API calls made with it will receive a `401 Unauthorized` response with an `expired_token` error code.

Implement proactive token refresh in your application to avoid mid-request failures. The pattern below tracks the expiry time and fetches a new token before it lapses:

<CodeGroup>

```javascript JavaScript
let tokenCache = null;

async function getAccessToken() {
  const now = Date.now();

  // Refresh if no token exists, or if it expires within the next 60 seconds
  if (!tokenCache || tokenCache.expiresAt - 60_000 < now) {
    const response = await fetch('https://api.trayce.io/v1/auth/token', {
      method: 'POST',
      headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
      body: new URLSearchParams({
        grant_type: 'client_credentials',
        client_id: process.env.TRAYCE_CLIENT_ID,
        client_secret: process.env.TRAYCE_CLIENT_SECRET,
        scope: 'verifications:read verifications:write',
      }),
    });

    const data = await response.json();

    tokenCache = {
      accessToken: data.access_token,
      // expires_in is in seconds; convert to a future epoch timestamp in ms
      expiresAt: now + data.expires_in * 1000,
    };
  }

  return tokenCache.accessToken;
}
```

```python Python
import time
import requests

_token_cache = {"access_token": None, "expires_at": 0}

def get_access_token():
    now = time.time()

    # Refresh if no token exists, or if it expires within the next 60 seconds
    if not _token_cache["access_token"] or _token_cache["expires_at"] - 60 < now:
        response = requests.post(
            "https://api.trayce.io/v1/auth/token",
            data={
                "grant_type": "client_credentials",
                "client_id": os.environ["TRAYCE_CLIENT_ID"],
                "client_secret": os.environ["TRAYCE_CLIENT_SECRET"],
                "scope": "verifications:read verifications:write",
            },
        )
        data = response.json()
        _token_cache["access_token"] = data["access_token"]
        # expires_in is in seconds
        _token_cache["expires_at"] = now + data["expires_in"]

    return _token_cache["access_token"]
```

</CodeGroup>

## Scopes

OAuth tokens honor the same scope system as API keys. Pass a space-separated list of scopes in the `scope` parameter of your token request. If you omit `scope`, the token inherits all scopes configured on the OAuth client in the Business Portal.

| Scope | Description |
|---|---|
| `verifications:read` | List and retrieve verification records |
| `verifications:write` | Create, update, and cancel verifications |
| `documents:read` | Retrieve uploaded documents associated with a verification |
| `documents:write` | Upload and delete documents |
| `webhooks:manage` | Create, update, and delete webhook endpoints |

Request only the scopes your integration requires for each token. Short-lived, narrowly-scoped tokens significantly reduce the risk of unauthorized access.

<Note>
  Treat your `client_secret` with the same care as a password. Store it in an environment variable or a secrets manager — never hard-code it in source files or commit it to version control. If a `client_secret` is ever compromised, rotate it immediately from **Business Portal** → **Settings** → **OAuth Clients** by clicking **Regenerate Secret** on the affected client.
</Note>

Identity verification is a core building block of trust in any digital product. Trayce's KYC (Know Your Customer) verification flow lets you confirm that a real person is who they claim to be — without you ever handling their sensitive documents directly. The individual receives a secure request in their Trayce Vault, submits their government-issued ID and a selfie, and Trayce returns a structured verification result you can act on.

<Steps>

  <Step title="Create a KYC Verification">
    Initiate a KYC check by sending a `POST` request to `/verifications`. Provide `type: "kyc"` along with a `subject` object identifying the individual. Trayce will look up or create a Vault for that person and send them a verification request.

    ```bash Request
    curl -X POST https://api.trayce.io/v1/verifications \
      -H "Authorization: Bearer <api_key>" \
      -H "Content-Type: application/json" \
      -d '{
        "type": "kyc",
        "subject": {
          "name": "Jane Doe",
          "email": "jane.doe@example.com"
        },
        "callback_url": "https://yourapp.com/webhooks/trayce",
        "metadata": {
          "internal_user_id": "usr_8821"
        }
      }'
    ```

    ```json Response
    {
      "id": "ver_01J3KZ2MXQP8TNVR4HSBW6FCD",
      "type": "kyc",
      "status": "pending",
      "subject": {
        "name": "Jane Doe",
        "email": "jane.doe@example.com"
      },
      "callback_url": "https://yourapp.com/webhooks/trayce",
      "metadata": {
        "internal_user_id": "usr_8821"
      },
      "created_at": "2024-07-15T10:22:31Z"
    }
    ```

    Store the returned `id` — you will use it to poll for the result or match incoming webhook events.
  </Step>

  <Step title="User Completes Verification">
    Once the request is created, the subject receives a push notification in their Trayce Vault app (or an email/SMS link if they haven't installed the app yet). The user then:

    1. Opens the Trayce Vault app and reviews your verification request, including your company name and the stated reason.
    2. Consents to share their identity information with your organization.
    3. Captures or uploads a photo of their government-issued ID (passport, national ID card, or driver's license).
    4. Takes a real-time selfie for liveness detection and face-matching against the ID document.

    Trayce handles all document capture, liveness checks, and data extraction on the user's device and within the Vault — your servers are never exposed to raw identity documents.
  </Step>

  <Step title="Poll or Wait for Webhook">
    You can receive the verification outcome in two ways: by polling the verification endpoint, or by listening for the `verification.completed` webhook event sent to your `callback_url`.

    **Option A — Poll the verification:**

    ```bash
    curl https://api.trayce.io/v1/verifications/ver_01J3KZ2MXQP8TNVR4HSBW6FCD \
      -H "Authorization: Bearer <api_key>"
    ```

    Check the `status` field in the response. It will be one of `pending`, `in_progress`, `completed`, or `failed`.

    **Option B — Webhook event:**

    When the verification finishes, Trayce sends a `POST` request to your `callback_url` with an event of type `verification.completed`. See the [Webhooks guide](/guides/webhooks) for payload structure and signature verification.

    ```json Webhook payload (example)
    {
      "event": "verification.completed",
      "webhook_id": "wh_9XKLT4NVQR",
      "created_at": "2024-07-15T10:31:07Z",
      "data": {
        "verification_id": "ver_01J3KZ2MXQP8TNVR4HSBW6FCD",
        "status": "completed",
        "result": "approved"
      }
    }
    ```
  </Step>

  <Step title="Read the Result">
    Fetch the completed verification to access the full result and extracted document details.

    ```bash Request
    curl https://api.trayce.io/v1/verifications/ver_01J3KZ2MXQP8TNVR4HSBW6FCD \
      -H "Authorization: Bearer <api_key>"
    ```

    ```json Response
    {
      "id": "ver_01J3KZ2MXQP8TNVR4HSBW6FCD",
      "type": "kyc",
      "status": "completed",
      "result": "approved",
      "subject": {
        "name": "Jane Doe",
        "email": "jane.doe@example.com"
      },
      "details": {
        "document_type": "passport",
        "document_number": "X8823041",
        "country": "FR",
        "date_of_birth": "1990-03-22",
        "verified_at": "2024-07-15T10:30:58Z"
      },
      "metadata": {
        "internal_user_id": "usr_8821"
      },
      "created_at": "2024-07-15T10:22:31Z",
      "updated_at": "2024-07-15T10:30:58Z"
    }
    ```

    A `result` of `"approved"` means the individual's identity was successfully verified. A `result` of `"rejected"` means verification failed — check the `details.rejection_reason` field for more information.
  </Step>

</Steps>

## KYC Request Parameters

<ParamField body="type" type="string" required>
  Must be `"kyc"` to initiate a KYC identity verification.
</ParamField>

<ParamField body="subject.name" type="string" required>
  The full legal name of the individual to be verified. Used to pre-fill the Vault request and match against the submitted identity document.
</ParamField>

<ParamField body="subject.email" type="string">
  The email address of the subject. Either `subject.email` or `subject.phone` must be provided — Trayce uses this to locate the subject's Vault or send an invitation.
</ParamField>

<ParamField body="subject.phone" type="string">
  The phone number of the subject in E.164 format (e.g. `+33612345678`). Either `subject.email` or `subject.phone` must be provided.
</ParamField>

<ParamField body="callback_url" type="string">
  An HTTPS URL to which Trayce will send webhook events for this verification (e.g. `verification.completed`). If omitted, you must poll the verification endpoint for status updates.
</ParamField>

<ParamField body="metadata" type="object">
  A free-form key-value object you can attach to the verification for your own internal reference (e.g. `internal_user_id`, `session_id`). Returned as-is in all responses and webhook payloads for this verification.
</ParamField>

## KYC Result Fields

<ResponseField name="id" type="string">
  The unique identifier for this verification (prefix `ver_`).
</ResponseField>

<ResponseField name="status" type="string">
  The current lifecycle status of the verification. One of `pending`, `in_progress`, `completed`, or `failed`.
</ResponseField>

<ResponseField name="result" type="string">
  The outcome of a completed verification. One of `approved`, `rejected`, or `review` (manual review required).
</ResponseField>

<ResponseField name="details.document_type" type="string">
  The type of identity document submitted by the user. One of `passport`, `national_id`, or `driver_license`.
</ResponseField>

<ResponseField name="details.document_number" type="string">
  The document number extracted from the submitted ID document.
</ResponseField>

<ResponseField name="details.country" type="string">
  The ISO 3166-1 alpha-2 country code of the issuing country (e.g. `"FR"`, `"US"`).
</ResponseField>

<ResponseField name="details.date_of_birth" type="string">
  The subject's date of birth in `YYYY-MM-DD` format, as extracted from the document.
</ResponseField>

<ResponseField name="details.verified_at" type="string">
  ISO 8601 timestamp of when the verification was completed and a result was determined.
</ResponseField>

<ResponseField name="details.rejection_reason" type="string">
  Present only when `result` is `"rejected"`. A machine-readable code describing the reason (e.g. `"document_expired"`, `"liveness_check_failed"`, `"name_mismatch"`).
</ResponseField>

---

<Note>
  In **sandbox mode**, KYC verifications skip the user Vault flow and return an instant mock result. Set `result` to `"approved"` or `"rejected"` in your request's `metadata.sandbox_result` field to control the simulated outcome. Sandbox API keys (prefixed `sk_test_`) always operate in this mode — no real user is ever notified.
</Note>

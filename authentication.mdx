Every request to the Trayce API must be authenticated. Trayce uses **Bearer token authentication** — you pass your credentials in the `Authorization` header of every HTTP request. Depending on your use case, you can authenticate with a static **API key** (simplest, ideal for server-to-server calls) or an **OAuth 2.0 access token** (for applications that act on behalf of users or need short-lived credentials).

<Warning>
  Never expose your API keys in client-side code, public repositories, or anywhere outside a secure server environment. If a key is compromised, rotate it immediately from the Business Portal under **Settings → API Keys**.
</Warning>

## API Keys

API keys are the quickest way to authenticate with Trayce. They are long-lived credentials tied to your Business Account and should only ever be used in server-side environments.

### Generating an API Key

1. Log in to the Business Portal at [app.trayce.io](https://app.trayce.io).
2. Navigate to **Settings → API Keys**.
3. Click **Generate New Key**, give it a descriptive label, and click **Create**.
4. Copy the key immediately — the full value is only shown once.

### Using an API Key

Pass your API key as a Bearer token in the `Authorization` header on every request:

```bash
Authorization: Bearer sk_test_4xKz9mQrPvLn2wJdTc8fYbHu
```

**Example request:**

```bash curl
curl --request GET \
  --url https://api.trayce.io/v1/verifications \
  --header "Authorization: Bearer sk_test_4xKz9mQrPvLn2wJdTc8fYbHu"
```

Trayce will return `401 Unauthorized` if the key is missing or invalid, and `403 Forbidden` if the key doesn't have permission for the requested resource.

## OAuth 2.0

OAuth 2.0 is available for applications that need to act on behalf of users, integrate with third-party identity providers, or prefer short-lived, rotatable access tokens over static API keys. Trayce supports the **Client Credentials** flow for machine-to-machine authentication.

### Obtaining an Access Token

Exchange your `client_id` and `client_secret` (available in the Business Portal under **Settings → OAuth Clients**) for a short-lived access token:

```bash curl
curl --request POST \
  --url https://api.trayce.io/v1/auth/token \
  --header "Content-Type: application/json" \
  --data '{
    "grant_type": "client_credentials",
    "client_id": "app_client_8Vz3nPqKmRdL",
    "client_secret": "cs_7YwJtNxBpFhQ2mCsLkUe9GdR"
  }'
```

A successful response returns an access token and its expiry:

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600
}
```

### Using an Access Token

Use the returned `access_token` exactly as you would an API key — pass it in the `Authorization` header:

```bash curl
curl --request POST \
  --url https://api.trayce.io/v1/verifications \
  --header "Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9..." \
  --header "Content-Type: application/json" \
  --data '{ "type": "kyc", "subject": { ... } }'
```

Access tokens expire after the number of seconds indicated by `expires_in` (typically 3600 seconds / 1 hour). Your application should request a new token before the current one expires, or handle `401` responses by re-authenticating automatically.

## Sandbox vs Production

Trayce provides separate environments for development and production. The environment is determined by the **prefix of your API key**.

| Key Prefix | Environment | Behaviour |
|---|---|---|
| `sk_test_` | Sandbox | Simulated verifications, no real data touched, no billing impact |
| `sk_live_` | Production | Real verifications, live identity checks, billed per request |

Always develop and test against the sandbox environment. Sandbox verifications process immediately using simulated outcomes, so you can test your integration logic, webhook handling, and error paths without any risk to real data or production billing.

When you're ready to go live, generate a `sk_live_` key in the Business Portal and update your environment configuration. No other code changes are required — the API surface is identical across both environments.

## Security Best Practices

Follow these practices to keep your API credentials secure:

- **Use environment variables** — never hard-code API keys or OAuth secrets in your source code. Load them at runtime from environment variables or a secrets manager (e.g. AWS Secrets Manager, HashiCorp Vault, or your platform's native secrets store).
- **Never expose keys client-side** — API keys must only ever be used in server-side code. Do not include them in browser JavaScript, mobile app binaries, or any code that could be inspected by end users.
- **Rotate keys regularly** — create new keys and retire old ones on a scheduled basis (e.g. every 90 days), or immediately if you suspect a key has been exposed.
- **Use the principle of least privilege** — if your Business Portal supports scoped keys, generate keys with only the permissions your integration actually requires.
- **Monitor for anomalies** — review the API activity logs in the Business Portal regularly. Unexpected spikes in request volume may indicate a compromised key.

<Warning>
  If you accidentally commit an API key to a public or shared repository, treat it as compromised immediately. Go to **Settings → API Keys** in the Business Portal, revoke the affected key, and generate a new one. Check your git history and remove the key from all commits before pushing again.
</Warning>

## Authentication Errors

| HTTP Status | Error Code | Description |
|---|---|---|
| `401 Unauthorized` | `invalid_token` | The `Authorization` header is missing, malformed, or the token is invalid or expired. |
| `401 Unauthorized` | `token_expired` | An OAuth access token has passed its `expires_in` window. Request a new token. |
| `403 Forbidden` | `insufficient_permissions` | The API key or token is valid but does not have the required scope for the requested operation. |

All error responses follow the same structure:

```json
{
  "error": {
    "code": "invalid_token",
    "message": "The provided API key is invalid or has been revoked.",
    "status": 401
  }
}
```
